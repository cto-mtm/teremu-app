## Principles

1. **The pipeline boundary is the invoice doc, not a new path.** Email ingestion ends where the scanner's upload ends: the source document in Storage (page JPEGs, or the body text for a body invoice) + an invoice doc in `processing`. Everything after extraction (arithmetic validation, Triage, approve/expense/discard, price roll, pantry) is untouched and unaware of the source beyond a `source` field. The only fork is *how the model reads the document*: text when the text exists, vision when it doesn't — both produce the same `OcrResult`.
2. **Cheap-first funnel.** Gmail's own query filters for free → a text-only LLM pass on headers/snippet → full extraction only for accepted candidates. Never send an attachment to a vision model that a $0.0001 text call could have rejected, and never send a picture of a page whose text we can read directly.
3. **One adapter boundary, like `llm.ts` and `pos/`.** All Gmail HTTP lives in `firebase/functions/src/email/gmail.ts` behind a narrow interface; the sync engine and classifier never see Google field names. A fixture-backed fake implements the same interface offline (no emulator exists for Gmail — same pattern as mock OCR without an API key).
4. **Compliance is the critical path, not code.** `gmail.readonly` is a Google **restricted scope**: verification + an annual paid CASA security assessment gate production. The engineering fits in the window; the verification may not — so the design keeps a no-OAuth forwarding fallback specified and the beta plan works inside Google's unverified-app limits.
5. **Junk must not pollute Triage or burn quota.** Every ingested message keeps a dedup/verdict record; OCR's own classify stage is the final guard (email-sourced `not_a_document` auto-discards); discarding an email-sourced invoice refunds its scan.

## OAuth & compliance (read this before writing any code)

**The scope.** `gmail.readonly` — read-only, includes attachment bodies. Verified 2026-08-05:

- Restricted-scope verification is a multi-week process (brand verification, demo video, scope justification) **plus** a security assessment under the App Defense Alliance's CASA framework, **re-done every 12 months** — [developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [support.google.com/cloud/answer/13465431](https://support.google.com/cloud/answer/13465431).
- CASA cost, from authorized labs: **TAC Security (Google's "preferred" partner) from ~$540/yr up to ~$1,800**; other labs (e.g. Leviathan, a CASA framework author) quote **$3,000–$6,000 per assessment** depending on scheduling — [switchlabs.dev pricing survey](https://www.switchlabs.dev/post/casa-tier-2-tier-3-security-review-providers-pricing-and-the-cheapest-option), [leviathansecurity.com/programs/google-casa-cloud-application-security-assessment](https://www.leviathansecurity.com/programs/google-casa-cloud-application-security-assessment). Budget **$540–$1,800/yr** via TAC; treat anything above as a negotiation failure.
- The CASA questionnaire is essentially OWASP ASVS-derived; our posture already matches most of it (no client DB credentials, server-side permission checks, tokens encrypted at rest per the design below). Prep is mostly documentation, not re-architecture.
- **Unverified-app limits shape the beta**: an OAuth app in *Testing* publishing status is capped at **100 test users** and — the one that actually bites — **refresh tokens expire after 7 days**, which breaks unattended daily sync weekly. Verification must be *in flight before Phase 1 code review*, and the beta either lives with weekly re-consent or waits for verification. (Exact current limits are re-verify items — see the checklist.)

**Alternatives considered:**

- **`gmail.metadata`** — insufficient: it cannot fetch attachment bodies (and restricts `messages.get` formats), so it can power classification but never ingestion. It is *also* on Google's restricted list, so it saves nothing on CASA. Rejected.
- **Plus-address forwarding (the escape hatch — cheap, keep it specified even though OAuth is the chosen path).** Each restaurant gets a unique ingest address (`facturas+{token}@in.teremu.com`); the owner sets a Gmail auto-forward filter (or hands the address to vendors directly). Inbound mail via any inbound-parse provider (SES / Postmark / Mailgun) → HTTPS webhook → **the exact same funnel from stage 1 onward** (the classifier and everything downstream are transport-agnostic by design). No OAuth, no CASA, no $540/yr, works with *any* mail provider, not just Gmail. Costs: user setup friction, Gmail's forwarding-confirmation dance, no backfill of existing mail. This is the Phase 0 de-risk: if verification slips past October, forwarding ships the user value on time and OAuth follows. The funnel/pipeline code is shared either way — only the fetch layer differs.

**Token storage.** Refresh tokens go in **Firestore, envelope-encrypted** — AES-256-GCM with a key from Secret Manager (`EMAIL_TOKEN_ENC_KEY`, `defineSecret`, key-version prefix on the ciphertext for painless rotation) — the exact scheme `pos.md` specifies for Square tokens, now one shared helper (`helpers/sealer.ts`, `makeSealer(envVar, …)`) with a key ring per integration.

**Secrets are bound** (2026-10-22): `EMAIL_SECRETS` (`EMAIL_TOKEN_ENC_KEY`, `GMAIL_CLIENT_SECRET`, exported from `email/index.ts`) is in the `secrets` of `api` and `emailSync`. A declared secret that does not exist in Secret Manager fails the deploy, so `node scripts/email-secrets.mjs` must have run on the project first (§Going live after Phase 0). The emulator runs without them, on the fake inbox and the dev key. Secret Manager itself is *not* a per-user token store (per-version pricing and admin overhead make it wrong for N users); it holds only the KEK. Access tokens are short-lived and cached in memory per invocation, never persisted. Tokens never appear in logs (a CASA check item).

**Revocation & re-consent.** Disconnect in Settings calls `https://oauth2.googleapis.com/revoke` and deletes the token fields. Google-side revocation (user removes access in their Google Account) surfaces as `invalid_grant` on refresh → connection flips to `needs_reauth`, Settings shows a reconnect banner, and the owner gets a `sendMail` alert — same lifecycle as `pos.md`'s `needs_reauth`. Nothing errors loudly in the background forever; sync just pauses.

## Provider abstraction

`firebase/functions/src/email/` — `types.ts`, `gmail.ts`, `fake.ts`, `sync.ts` (engine), `classify.ts` (funnel stages 0–1), `ingest.ts` (attachment or body → source document + extraction path → invoice doc), `pdf.ts` (text layer + rasterization), `body.ts` (HTML → plain text), `oauth.ts` (connect/callback/disconnect routes).

```ts
interface MailProvider {
  authUrl(state: string): string
  exchangeCode(code: string): MailTokens            // + accountEmail, accountSub
  refresh(tokens: MailTokens): MailTokens
  revoke(tokens: MailTokens): void
  listMessageIds(tokens, query, cursor): { ids: string[], cursor: string | null }
  listHistory(tokens, startHistoryId): { added: string[], newHistoryId: string } | "expired"
  getMessageMeta(tokens, id): MailMessageMeta        // headers, snippet, attachment manifest
  getMessageBody(tokens, id): { text: string | null, html: string | null }  // body candidates only
  getAttachment(tokens, messageId, attachmentId): Buffer
}
```

`MailMessageMeta` — `{ id, rfc822MessageId, from, to, subject, snippet, internalDate, attachments: [{ attachmentId, filename, mimeType, sizeBytes, inline }] }`. Normalized, provider-blind; the forwarding fallback produces the same shape from a webhook payload.

Vocabulary (in `shared/src/vocab.ts`, per the schemas rule): `invoiceSourceSchema = z.enum(["scan", "email"])` — the invoice doc gains `source` with `.catch("scan")` so every pre-existing doc reads as a scan; and email ingestion uses the same **`integrations` perms area** `pos.md` already plans (`none | read | edit`; owners bypass) — add it once, both features check it.

## Identity model (inbox ≠ restaurant, but stricter than merchant ≠ location)

`pos.md`'s merchant/location split does not transplant directly: a Square merchant *partitions* into locations; an inbox does not — a message has no location on it. So:

- `emailConnections/{gmail_{sub}}` (top level, keyed by Google account subject — stable across email renames) — **the only doc per inbox** (as built in Phase 1, `email/store.ts`): provider, accountEmail, `rid` (the one restaurant it feeds; null once disconnected) + `previousRid`, connecting `uid`, sealed refresh token, granted scopes, status (`active | needs_reauth | revoked`), epoch, `sync` (`backfillFrom`, `backfillCursor`, `backfillDone`, `historyId`, `lastInternalDate` — null until Phase 2's first sync), `lastSyncAt`, timestamps. A restaurant's inboxes are the query `rid == {rid}`; there is no per-restaurant pointer doc to keep in step, and Max's three inboxes are just three connection docs. `paused_quota` (Phase 3) will be a flag next to `status`, not a status: a paused inbox is still connected.
- Restaurant-level email settings (future sender allow/blocklists — the backfill window is a constant, not a setting) and monthly ingest counters land in Phase 2–3 when something reads them.
- **v1 invariant: one inbox ↔ one restaurant.** Attaching the same Gmail account to two restaurants would duplicate every invoice into both, and there is no per-location signal in the mail to route by. Connect-time check: if the connection doc already points at another rid, refuse with explicit copy ("esta bandeja ya está conectada a {name}"). The multi-location owner with one inbox connects it to the flagship; **sender → location routing rules** are the honest later answer (listed under Later), not a v1 hack.
- The connection stores *who* connected (`uid`) for audit, but ingested invoices are not "uploaded by" anyone — the invoice doc records provenance instead: `email: { messageId, rfc822MessageId, from, subject, receivedAt, connectionId }`. Any staff member with triage perms reviews them, same as scans.
- Staff/shared-inbox reality (a gestoría or an office manager mailbox): whoever holds `integrations: edit` (or the owner) connects whatever inbox they control. The classifier + Triage + discard-refund make a noisy inbox survivable; routing precision is the owner's choice of which inbox to connect.
- **Disconnect** (per restaurant, which under the v1 invariant is per connection): revoke token, delete token fields, connection becomes a tombstone (status `revoked`, epoch kept). **Ingested invoices are retained** — they are the restaurant's own records; UI copy states this. The `emailIngests` dedup records are also retained so a later reconnect of the *same* account never re-ingests old mail; reconnecting a *different* account is a different connection doc, so old dedup state simply doesn't apply (epoch bump covers the same-doc/different-grant edge). Full purge rides `DELETE /restaurants/:rid` recursive delete.

## Sync engine

**As built (Phase 2) — where it differs from the plan below:** the scheduler (`emailSync`) ticks **every 60 minutes**, not 6 hours, so an unfinished backfill (always due) lands within hours; the per-plan interval still decides when a finished inbox syncs. A sync holds a lease on the connection (`syncLeaseUntil`, 9 min) so the scheduler and "check now" never walk the same cursors; cursors are written only while the connection's `epoch` is unchanged. Dedup ids are `{connectionId}_{messageId}` (two Max inboxes can't collide). The verdict set gained `candidate` (passed stage 0, waiting for stage 1 — the daily cap or a failed batch leaves it there; three failed batches → `failed`), `duplicate` (same RFC-822 Message-ID as a recorded message) and `gone` (deleted from the mailbox before we could read it — adapters throw `MailNotFoundError` on a 404, and the engine records the message instead of failing the sync, or one deleted email would stall the inbox forever); `accepted` waits for Phase 3. When History has expired, the re-list anchor (`lastInternalDate`) only moves once the whole re-read finishes: the listing runs newest first, so moving it mid-pass would skip the older messages a budget-cut pass hadn't reached. Body HTML goes through the shared `helpers/html.ts` converter (also the listing import's), with table cells kept tab-separated. Data kept per record is minimized: a skipped message keeps only its date, a rejected one drops its preview. Adapters flag `excluded` on message metadata (Gmail: SPAM/TRASH/CHAT/SENT/social/forums labels), because History returns mail the listing query would never list. The stage-0 allowlist reads `restaurants/{rid}/emailSenders/{address}.kinds`; approval writes it in Phase 3. Composite index: `emailIngests (connectionId, verdict, internalDate desc)`; the waiting list across a restaurant's inboxes (`waitingItems`, `GET /email/waiting`) adds `emailIngests (verdict, internalDate desc)`.

**As built (Phase 3) — where it differs from the plan below:** an ingest pass runs at the end of every sync (scheduler: 20 documents per inbox per tick; "check now": 3, to answer inside the API timeout); a backlog sets `ingestPending` on the connection, which keeps the inbox due, and so does a quota pause (`quotaPausedPeriod`), so an upgrade takes effect on the next hourly tick even when nothing told the engine (a plan written straight to Firestore); a plan change through Stripe or `PUT /billing/plan` lifts it at once (§Triage integration). Per document the order is read → choose path → `consumeScan` → write pages/text + doc → extract: nothing is written for a document the meter refuses. Expired deferred messages are swept first each pass (a paused pass stops at its first refusal and would never reach them). Every PDF is rasterized for Triage even on the text path; emailed photos go through `normalizeImage` (≤1600px JPEG). Unreadable files become `failed / unreadable` docs with no `scanPeriod`. The nudge mail's once-a-month guard is `restaurants/{rid}.emailQuotaNudged`, set in a transaction before sending (the mailer's idempotency key cannot carry a changing count). `possible_duplicate` runs for every invoice, scans included — **the real-corpus suite (`npm run test:real`) pins warnings and may need `-u` if two corpus documents share vendor, date and total.** The offline text mock is seeded from the text, so the same document reads the same.

**PDF spike (2026-10-21, the 248-PDF real corpus, Node 22, pdfjs-dist 6.3.289 + @napi-rs/canvas 1.0.9 pinned exactly):** pdfjs imports in ~130 ms; text extraction ~1 ms/doc (p95 ~50 ms); a 1600px page renders in ~1.2 s to a ~180 KB JPEG. 88 documents pass the text-layer gate, 160 go `vision` (4 had text on only some pages → `vision`, as designed); every page sat at 0 characters or ≥ 150, so the threshold falls in an empty gap. With pdf.js's gap-spanning whitespace items skipped, all 88 come back with tab-separated table rows. That corpus is mostly scans an accountant gathered — emailed PDFs should skew more digital; measure it once real inboxes sync.

**Scheduling.** One `onSchedule` v2 function in **us-east1** (`REGION`, like everything else), `schedule: "every 6 hours"`. Each tick iterates `emailConnections` where status is `active`, sequentially (connection counts will be small for a long time; parallelize later if ticks run long), and syncs a connection only when it is **due for its plan**: `now − lastSyncAt ≥ PLAN_LIMITS.emailSyncHours` — **24 h on Free, 6 h on Pro/Max** (`plan.ts`, next to `assistantTurns`; the POS precedent of an adaptive per-plan cadence on one scheduler). An unfinished backfill is always due, on every plan, so the first 31 days land within hours of connecting rather than over a month of daily ticks. 6 h costs nothing extra on paid plans (stage 0 is free, stage 1 is fractions of a cent) and makes the feature feel alive; daily on Free is plenty for invoices and keeps the free loop light.

**Backfill: 31 days, once.** On connect, the first sync is query-based with `after:` = connect time − **31 days** (`BACKFILL_DAYS = 31`, a constant: a full billing month plus a day, so "last month's invoices" are always all there; enough to feel magical, bounded enough to never swallow a decade-old mailbox). The resolved `backfillFrom` timestamp is stored on the connection. Pagination 100 ids/page; the backfill is **chunked and resumable** exactly like `pos.md`'s: each tick processes up to ~200 new messages per connection, checkpointing the page cursor on the connection doc, until caught up — then `backfillDone: true` and it never runs again for that connection. Within the backfill, messages are processed **newest first**, so a quota cap (Free's 25) is spent on the most recent invoices.

**After the backfill: incremental only — never a rolling 31-day re-scan.** Re-reading a month of mail every tick would re-list and re-classify the same messages over and over; the dedup gate would stop double-ingestion, but the Gmail units and classifier calls would be wasted. Steady state uses `history.list` from the stored `historyId` (2 quota units — near-free) to get new message ids. Gmail expires history (typically ~a week); on `expired`/404 fall back to query-based sync from the **last cursor**, not from 31 days back: `messages.list` with

```
q = "after:{lastInternalDate/1000} -in:spam -in:trash -in:chats -from:me -category:social -category:forums"
```

then advance both cursors. The query deliberately has **no `has:attachment`**: body invoices have no attachment, and stage 0 (below) is where non-candidates are dropped. `category:promotions` is *not* excluded — Gmail files some SaaS and supplier invoices there.

**Reconnect.** Reconnecting the *same* account does not re-run the backfill (`backfillDone` lives on the connection doc, and the `emailIngests` dedup records would skip everything anyway). A *different* account is a new connection and gets its own 31 days.

**Quota math (verified against [developers.google.com/workspace/gmail/api/reference/quota](https://developers.google.com/workspace/gmail/api/reference/quota), updated by Google 2026-05-01):** per-project 1,200,000 units/min; **per-user 6,000 units/min**; `messages.list` 5, `messages.get` 20, `attachments.get` 20, `history.list` 2, `users.watch` 100; free below a new 80M units/day billing threshold. Dropping `has:attachment` means every message in the window gets a metadata fetch. A 600-email/mo inbox costs ~`6×5 + 600×20 (metadata) + 150×20 (bodies) + 150×20 (attachments) ≈ 18K units` for the *full 31-day backfill* and ~50–300 units per steady-state tick — still two to three orders of magnitude under the limits. Still: page sequentially per user (community-reported per-user burst limits ~250 units/sec exist), exponential backoff on 429, and never fan out attachment fetches concurrently per mailbox.

**Dedup.** `restaurants/{rid}/emailIngests/{gmailMessageId}` — written **before** any processing (create-if-absent is the idempotency gate; a crashed tick re-runs safely). Fields: `rfc822MessageId`, from, subject, `internalDate`, `verdict` (`skipped_prefilter | classified_no | ingested | deferred_quota | expired_quota | failed`), `path` (`text_layer | vision | body | null`), `invoiceId | null`, classifier confidence, epoch, timestamp. The Gmail message id dedupes within the mailbox; the RFC-822 `Message-ID` header additionally catches the same message arriving twice (forwarded copies) — checked with a bounded query before ingesting. These records double as the funnel's observability: junk-rate and precision are one collection-group count away.

**Documents and extraction paths.** For each accepted message, each candidate becomes one invoice doc and takes exactly one of three paths (recorded as `path` on the dedup record and as `extraction` on the invoice doc, so precision and cost are measurable per path):

| Path | Source | What the model gets | What Triage shows |
|---|---|---|---|
| `text_layer` | PDF whose pages carry real text (billing-software output — expected to be the majority of emailed invoices; measure it) | The PDF's text, page by page | Rasterized page images, as for a scan |
| `vision` | Scanned PDF, or an image attachment | Page images (the existing OCR, on the `vertex` backend) | Page images |
| `body` | No candidate attachment; the invoice is written in the message itself | The body converted to plain text | The body text |

- **PDF text layer first.** `pdf.ts` opens the PDF with **`pdfjs-dist`** (legacy Node build) and reads each page's text (`getTextContent`, items joined in reading order with line breaks on y-jumps so table rows stay rows). The PDF qualifies for `text_layer` when **every** page yields ≥ ~150 non-whitespace characters and the text contains digits; otherwise the whole document goes `vision` (no per-page mixing — one path per document keeps the extraction and the debugging simple). Text is capped at ~24K characters per document (≈ 10 dense pages); a longer text goes `vision` with the page cap below. Why text first: every character arrives exactly as printed — no misread digits, which is where vision OCR loses totals — and it is ~25–30% cheaper per page (the cost table below). It also works on any provider, including text-only models.
- **PDF pages for display (and for `vision`).** Every PDF is still rasterized, **one JPEG per page**, into `receipts/{rid}/…` using the multi-page layout for `imagePaths` (do not invent a second layout): Triage always shows the document the reviewer is approving. Rasterizer: **`pdfjs-dist` + `@napi-rs/canvas`** — pure npm install, prebuilt native binary, no system packages, works in Cloud Functions; both stay `external` in `esbuild.mjs` like the other runtime deps. Render capped at **1600px long edge, JPEG q≈80** — the same ceiling as the app's `downscaleReceipt`, which `llm.md` calls out as a *cost control*, not just bandwidth: it is what keeps a page at ~1.5K image tokens on the `vision` path. Rasterizing costs CPU, not tokens.
- **Images** (vendors who photograph the invoice into the mail, including inline parts): `image/jpeg|png` attachments ≥ ~100 KB *and* plausibly document-sized are pages, always `vision`; tiny inline logos/signatures are skipped by the size gate.
- **Body invoices.** A message with no candidate attachment that stage 1 accepts is fetched in full (`getMessageBody`). `body.ts` prefers the `text/plain` part; otherwise it converts the HTML to text — tags stripped, table cells separated by tabs and rows by newlines (invoice tables must survive), scripts/styles/images dropped, quoted reply chains and signatures trimmed by the usual markers (`El … escribió:`, `On … wrote:`, `-- `). Capped at ~12K characters. The text is stored as `receipts/{rid}/{invoiceId}/text.txt` and referenced by `email.textPath` on the invoice doc (a `text_layer` document stores its text the same way, so a reprocess can read it again); `imagePaths` is empty. Nothing is rendered to an image — an HTML-to-image renderer (headless Chrome) would be the heaviest dependency in the functions bundle for a document type the text path already reads perfectly.
- **Limits**: skip attachments > 10 MB; at most **8 pages** per PDF, the multi-page cap (warn on the invoice when truncated); at most 3 candidate attachments per message (each becomes its own invoice doc — a message carrying two vendor PDFs is two documents; the body is only a candidate when there is no candidate attachment). Password-protected/corrupt PDFs → invoice doc created with `status: "failed", error: "unreadable"` so it *surfaces* in Triage instead of vanishing — no quota charged (see ordering below).
- **Handoff**: the worker writes the source document (page images and/or `text.txt`), **then** creates the invoice doc (`status: "processing"`, `source: "email"`, `extraction`, provenance block) and invokes the pipeline entry point directly — *not* via the Storage trigger, which exists for app uploads and would fire once per page. The pipeline gains one sibling to `processInvoiceImage`: `processInvoiceText(rid, invoiceId, text)`, which calls a new **`extractInvoiceFromText`** in `ocr.ts` — the same extraction prompt and known-ingredients catalog minus the image part, label **`ocr-text`**, the same lenient zod parse and mock-when-no-key behavior. It is the `extractMenu` / `extractMenuFromText` pair (`menuscan.ts`) applied to invoices. From the parsed `OcrResult` onward the two entry points share everything (arithmetic validation, `invoicePatchFromOcr`, FX, warnings).

**Ordering per document**: write source → choose path → `consumeScan` → extract. Quota is charged only for documents that actually reach the model, whichever path they take.

## AI classification funnel (cheap-first)

**Stage 0 — free.** The Gmail *query itself* is the first filter (spam/trash/chat/self/social/forums excluded — zero tokens, zero units beyond the list call). On the metadata, a message is a candidate if **either**:

- it has a **candidate attachment** (PDF, or a big image — the size gate above), or
- it has none, but its **subject or snippet** carries invoice vocabulary — *factura, nº de factura, albarán, recibo, importe, total, IVA, invoice, receipt, amount due* — the **body-candidate** gate. The word lists are language data in `classify.ts` (es/en), not country data, so they don't belong in a country pack.

Everything else is `skipped_prefilter`. **Fast-path allowlist**: a sender whose previous email invoice was *approved* skips stage 1 and goes straight to extraction — on the same path type as last time (an attachment sender stays an attachment sender; a body sender's mail is only fast-pathed when it again has no attachment). Expected to eliminate 60–70% of a real inbox before any model sees anything; the body gate lets a little more through than `has:attachment` did, which stage 1 absorbs.

**Stage 1 — text-only LLM classification.** One batched call per ~25 messages through `chatCompletion` on the **`vertex` backend** (Gemini on Vertex — every call on email data goes there, including the page images of an emailed PDF or photo since 2026-10-28, so nothing from Gmail reaches the default provider; docs/llm.md §Two backends) (label `email-classify`, `json` structured output, mock verdicts offline — all per `llm.md`; **provider stays env config, nothing Gmail-specific reaches `llm.ts`**). Input per message: From, Subject, Gmail snippet (~200 chars), attachment filenames + sizes — ~120–150 tokens; **body candidates** also send the first ~600 characters of the body text (one extra `messages.get` each, ~+150 tokens); prompt ~350; output `{ id, isInvoice, confidence, vendor, amount }` ~35 tokens/message (2026-10-29: `vendor` — the supplier's name as the mail writes it, ≤ 60 chars — and `amount` — `{ value, currency }` only when the subject or preview quotes the total with a currency, "never guess" — are hints for the paywall's teaser, ≈ 15 output tokens, well under $0.0001/message; the offline mock reads the amount from the preview with a regex and leaves `vendor` null). What each record keeps: an `accepted` message keeps its preview and the hints (`vendorHint`, `amountHint`) while it waits; `classified_no` keeps neither; once a message is `ingested`, `expired_quota` or `gone` it drops both (`PREVIEW_FIELDS` in `sync.ts`). Threshold ~0.6 to ingest; es/en prompt examples must cover *factura, albarán, recibo, recibo de alquiler and utility / fuel bills (accept — since 2026-10-28; a vendor bill paid by direct debit is still a bill), estado de cuenta (reject), pedido/confirmación (reject), marketing (reject)* — and for bodies, *payment confirmations and shipping notices that quote a total (reject unless they itemize what was bought)*. Per-message cost at Gemini 3.1 Flash-Lite ($0.25 in / $1.50 out per 1M, re-verified 2026-08-05 — matches `llm.md`, checked 2026-07-24; note Google retires 2.5 Flash-Lite 2026-10-16, our preset is already 3.1): **≈ $0.00007/message**, ≈ $0.0001 for a body candidate.

**Stage 1 has a daily cap per restaurant** (`helpers/dailyCap.ts`, the listing import's pattern): **50 classified messages/day on Free, 300 on Pro/Max**. A real inbox never reaches it after the backfill; a flood inbox (newsletters with "factura" in every subject) just spreads over days instead of spending. Candidates past the cap wait for the next tick, unclassified. This is what bounds a free inbox's classifier cost when the scan cap is not the binding limit (below).

**Stage 2 — full extraction, on the document's path.** `vision`: ~$0.0025/page (the `llm.md` verified figure at ≤1600px). `text_layer`: ~$0.0018/page — the image tokens are replaced by text tokens of about the same count, and output (the line items) dominates either way, so the saving is ~25–30%; the bigger win is exact characters. `body`: ~$0.0015/document (one page of text, usually short). OCR's own classify stage (`kind: receipt | other`) is the final guard on all three paths: an email-sourced invoice that comes back `not_a_document` is **auto-discarded** (status `discarded`, scan refunded) instead of `failed` — a scan-sourced failure means "retake the photo", an email-sourced one means "the classifier was wrong", and the user should not have to clean that up.

Token budget per stage (per message / per document):

| Stage | Input tokens | Output tokens | Cost each |
|---|---|---|---|
| 0 · query + heuristics | 0 | 0 | $0 (≤ a few Gmail quota units) |
| 1 · text classify | ~135/msg, ~285 for a body candidate (+ prompt amortized) | ~20/msg | ~$0.00007/message (~$0.0001 body) |
| 2 · extract, `vision` | ~2.7K/page (image ~1.5K + prompt + catalog) | ~800/page | ~$0.0025/page |
| 2 · extract, `text_layer` | ~2.2K/page (text ~1K + prompt + catalog) | ~800/page | ~$0.0018/page |
| 2 · extract, `body` | ~1.7K/doc (body text ~500 + prompt + catalog) | ~700/doc | ~$0.0015/document |

A stage-2 call is ~20–35× a stage-1 call; stage 1 rejecting one marketing PDF pays for ~35 classified messages. That ratio is the whole reason the funnel exists.

## Triage integration

- **Invoice doc changes** (both `models.ts` strict and `app/src/lib/schemas.ts` lenient, mirrored by design): `source: invoiceSourceSchema.catch("scan")`; `extraction: z.enum(["vision", "text_layer", "body"]).catch("vision")` (vocab, so it lives in `shared/src/vocab.ts`); optional `email` provenance block (`messageId, rfc822MessageId, from, subject, receivedAt, connectionId, textPath?`); `scanPeriod` + `scanRefunded` (the month whose scan it spent, and whether discard gave it back); a new warning code `possible_duplicate` (below). Triage renders `needs_review` docs it already knows how to render, plus a small source badge ("📧 correo") and the sender/subject line in the detail view.
- **The one new Triage view: a body invoice has no images.** Where the detail view shows page images, a doc with `extraction: "body"` shows the stored body text instead (monospace, scrollable, tables kept by the tab/newline conversion). Everything else on the review screen — line items, totals, warnings, approve/expense/discard — is unchanged. `text_layer` docs need nothing new: they have page images like any scan.
- **Quota: emailed documents consume the scan quota, on every plan.** Same inference cost, same value metric ("documents digitized" is what the meter always really was); exempting email would let a 600-email inbox out-cost a capped scanner and make the tiers incoherent. One scan per *document* whatever its path (not per page — matches how `consumeScan` meters `POST /invoices` today; multi-page multiplies inference, not quota, which is a deliberate simplification `business-model.md` can absorb at these margins). **On Free this meter is the feature's cap**: 25 documents a month, photos and email combined.
- **Junk protection, three layers**: (1) the funnel keeps false positives to a trickle; (2) auto-discard on OCR `not_a_document` with refund; (3) **discarding an email-sourced invoice refunds its scan** — a small transactional decrement in the discard handler, same period only. The discard flow already exists (`PUT /invoices/:id/discard`); refund-on-discard means a misfire costs the user one tap and zero quota, which is what makes auto-ingestion tolerable at all.
- **Quota exhaustion pauses, never silently drops**: when `consumeScan` refuses, the connection flips to `paused_quota`; sync and classification continue (bounded by stage 1's daily cap), but accepted candidates get verdict `deferred_quota` instead of being extracted. Settings shows the count, and the owner gets one `sendMail` nudge per period — the single best upgrade prompt this feature produces, and on Free the expected one: "12 facturas esperando en tu correo". Because classification keeps running, that number is real invoices, not raw candidates. Next period, deferred candidates are retried newest first — **if they arrived within the last 31 days**; older ones become `expired_quota` (counted in Settings, never extracted), so a Free restaurant that stays capped for months does not build an unbounded backlog. Upgrading mid-period lifts the pause at once: `resumeAfterPlanChange` (`email/planChange.ts`, from the Stripe webhook and the emulator's `PUT /billing/plan`) clears `quotaPausedPeriod` and sets `ingestPending` on every paused inbox, so it reads `working` and the open Settings card drains it; the always-due hourly retry stays the guarantee for a plan written straight to Firestore. A pause stamped in a month that is over is cleared on the next sync even with nothing left to import (it used to keep a Free inbox syncing hourly). As built: each refused scan writes `restaurants/{rid}.emailQuota = { period, waiting }` (accepted + deferred across the restaurant's inboxes; cleared with the pause), shipped as `GET /me` `emailWaiting`; `expired_quota` is counted per inbox in `GET /email` (`expired`) and shown on the card; the sync response says `paused` and `expired`. The monthly mail knows the plan: an upgrade nudge to `/pricing?reason=email_quota` with the unsubscribe link, or on Max a plain notice that points at `/settings?card=email`, not promotional.
  - **Upgrade handoff** (the app): one component, `UpgradeNotice.vue`, is the paywall wherever invoices wait — the email card ("12 facturas esperando en tu correo. Con Pro entran hoy."), the Settings Plan card (a line beside "Mejorar tu plan"), a dismissible banner in Triage, and the pricing page's context strip when the owner arrives from one of them (`?reason=email_quota`, or `email_free` from the Free cap hint). Checkout from there returns to `/settings?card=email` (`returnCard`); when the plan rises with the card open it drains the backlog and says how many came in. Never on Max: nothing to upgrade to.
  - **The teaser — what waits, by name** (Phase 4): `GET /email/waiting` (`triage` or `integrations` read) returns the waiting count, the senders by frequency (display names, `senderName`), the newest ten messages (sender, subject, date, file, kind, hints) and `amountTotal` — the hints added up only when every one is in the restaurant's base currency, else null. The email card's and Triage's notices list up to five as locked rows (`WaitingInvoiceRow.vue`, a hint shown in its own currency, never converted) and "y N más"; Triage puts the first three at the top of the queue as dashed ghost cards ("Esperando tu plan"; a tap takes the owner to the plans, anyone else to the banner; none on Max); the pricing strip names the senders ("Hoy entrarían facturas de Makro, Coca-Cola y 3 proveedores más") with "unos 1.900 €" when there is a total; the monthly mail names the first three senders and the total. No extraction is spent on a waiting document — showing locked, pre-read invoices is the out-of-scope level "B".
- **Duplicates (emailed and photographed)**: undetectable pre-OCR (different pixels). Post-OCR, before flipping to `needs_review`: if an existing non-discarded invoice matches on (vendor name key, invoice date, total ±2%), attach `possible_duplicate` — a warning like the arithmetic ones, guiding the reviewer's eye, never blocking. Works in both directions regardless of which copy arrived first.

## AI cost & business-model impact

Model of a realistic restaurant inbox at Gemini 3.1 Flash-Lite prices ($0.25/$1.50 per 1M — see `llm.md`). Assumptions: prefilter passes 40% of mail; classifier false-positive load ≈ +20% of true invoices; 1.5 pages/document average (emailed PDFs are longer than photos); $0.0025/page OCR; $0.00007/message stage 1. The table prices **every** document on the `vision` path — the conservative case. The 2026-10-21 changes move it in both directions and roughly cancel: body candidates make stage 1 ~20–40% dearer (still cents), while `text_layer` and `body` documents are ~25–40% cheaper to extract than `vision`. If half of emailed documents turn out to be digital PDFs, stage 2 drops ~15%. Treat the table as an upper bound until `llm_usage` (labels `ocr`, `ocr-text`, `email-classify`) gives real numbers per path.

| Inbox / month | Emails | Real invoices | Stage-1 msgs (×40%) | Stage-1 cost | Docs OCR'd (×1.2) | Pages (×1.5) | Stage-2 cost | **Email AI total** | Photo-only equivalent | Delta |
|---|---|---|---|---|---|---|---|---|---|---|
| Light | 200 | 20 | 80 | $0.006 | 24 | 36 | $0.090 | **≈ $0.10** | $0.05 | +$0.05 |
| Typical | 400 | 40 | 160 | $0.011 | 48 | 72 | $0.180 | **≈ $0.19** | $0.10 | +$0.09 |
| Heavy | 600 | 60 | 240 | $0.017 | 72 | 108 | $0.270 | **≈ $0.29** | $0.15 | +$0.14 |

Readings:

1. **Marginal AI cost is noise**: the heaviest realistic inbox adds ~$0.29/mo — under 1% of Pro ($39) and invisible next to the ~$1.50 all-in cost of a typical Pro (`business-model.md` §4). Classification is ~6% of the total; OCR dominates, and OCR was going to happen anyway if the user photographed the same invoices. The *incremental* cost of the feature over photo-scanning the same documents is $0.05–0.14/mo, driven by false positives and PDF page counts.
2. **The real cost is fixed, not marginal**: CASA at $540–$1,800/yr = **$45–$150/mo of fixed COGS** — equivalent to the *entire inference bill of 150–500 typical restaurants*. At Pro's ~$25 contribution margin, the assessment is covered by **2–6 Pro subscriptions**. The first version of this doc used that to gate the feature to paid plans. That was backwards: a fixed cost is paid the same whether 5 or 5,000 restaurants connect, so keeping Free out saves nothing on it — it only shrinks the funnel that pays it back. What a Free connection adds is its *marginal* cost, below.
3. Gmail API itself: $0 (comfortably below the 80M units/day billing threshold).

**A Free inbox, worst realistic case.** Classification on a 600-email inbox: ~240–300 stage-1 messages ≈ $0.02–0.03. Extraction is capped by the meter at 25 documents ≈ 38 pages ≈ $0.09 on `vision`, less on the text paths. **≈ $0.12/month** for a connected Free restaurant at its cap. The flood case (an inbox that keeps every candidate gate open) is bounded by stage 1's daily cap: 50/day × 30 × $0.0001 ≈ $0.15 of classification, so **≈ $0.25/month absolute worst**. And most of the 25 documents replace photos the user would have scanned within the same cap, so the cost *added by email* is closer to **$0.03–0.05**.

**Recommended business-model adjustments:**

| Decision | Recommendation |
|---|---|
| Which tiers | **All, Free capped** (2026-10-21, Luis). Free: 1 inbox, daily sync, documents count toward its 25 a month. Same shape as POS on Free (on every plan, Free capped — `pos.md` §Plan gating). "Your invoices enter themselves" is the strongest *activation* moment this product has, and hitting the cap with invoices visibly waiting is the strongest *conversion* moment — Free needs to feel both |
| Tier differentiation | Free: **1 inbox, every 24 h** · Pro: **1 inbox, every 6 h** · Max: **up to 3 inboxes, every 6 h** (multi-location owners, the segment Max targets). In `plan.ts` `PLAN_LIMITS` as `emailInboxes` and `emailSyncHours`. The real Free → Pro lever is the 25-document meter, not the cadence |
| Do emailed docs count as scans? | **Yes, on every plan** — same meter, one scan per document whatever the extraction path, refund on discard. Rename the user-facing concept from "escaneos" to "documentos" when this ships |
| Quota numbers | **Unchanged** (Free 25 / Pro 500 / Max 1,500): a heavy inbox is 60–72 docs/mo ≈ 14% of Pro's quota even *added to* heavy photo scanning; on Free a typical inbox alone (~48 docs) fills the meter, which is the point |
| Gross-margin impact | Pro serving cost rises from ~$1.50 → ~$1.70 typical (~+$0.19); margin on $39 goes from ~96% to ~95.5% — no price action needed. The CASA fixed cost wants ≥ ~6 Pro subs before this feature is margin-neutral; below that it's a deliberate CAC-like investment |
| Free-tier note | A connected Free restaurant costs ~$0.12/month more at its cap, ~$0.25 at the absolute worst. Even if *every* free user connected a flood inbox, the free-user cost in `business-model.md` §9 goes from ~$0.20 to ~$0.45 and the Gemini free-rider ceiling from 128:1 to ~57:1 (conversion floor 0.8% → ~1.8%) — still under the healthy 4–8%. Realistically most free restaurants never connect, so the blended change is a few cents |

## Abuse & edge cases

- **Huge mailbox on first sync**: fixed 31-day backfill, once + per-tick message budget + cursor checkpointing + stage 1's daily cap. No invocation ever swallows a decade of mail, and no tick re-reads the month.
- **Free accounts are free to create**: a script that signs up many Free restaurants and connects inboxes gets, per restaurant, at most 25 extractions and 50 classifications a day — the same per-account bound the listing import relies on. The project-wide backstop is the same too: a budget alert, plus the `llm_usage` per-label metric watched for `email-classify` spikes.
- **Shared/accountant inboxes**: high junk mix is survivable (funnel + discard-refund); the wrong-restaurant problem is answered by the one-inbox-one-restaurant invariant and, later, sender-routing rules.
- **Statements, price lists, order confirmations, marketing**: stage-1 prompt rejects them by name (Spanish vocabulary matters: *estado de cuenta*, *tarifa*, *confirmación de pedido*); whatever leaks through hits OCR's `not_a_document` auto-discard.
- **Same invoice emailed and photographed**: `possible_duplicate` warning post-OCR (vendor+date+total match), reviewer decides, discard refunds.
- **Invoices in the email body** (SaaS vendors, small suppliers who type the order into the mail): **in v1** on the `body` path — read as text, shown as text. Messages that quote a total but aren't invoices (payment confirmations, shipping notices) are the body path's typical false positive: stage 1 rejects them by name, OCR's `not_a_document` and discard-refund catch the rest. Watch the `body` path's discard rate separately in the junk telemetry.
- **A body that is only a cover note** ("adjunto factura") with the PDF attached: the attachment wins — the body is only a candidate when there is no candidate attachment, so this is one document, not two.
- **Image-only PDFs that look digital** (a scan saved as PDF, or text rendered as outlines): fail the text-layer gate on character count and go `vision` — correct by construction.
- **Multiple attachments per message**: up to 3 candidates, each its own invoice doc (a vendor emailing factura + albarán together yields both, and reconciliation already pairs them).
- **Password-protected/corrupt PDFs**: surfaced as `failed / unreadable` in Triage, no quota charged.
- **Gmail won't hand a message over**: a 403 is classified by Google's reason (`gmail.ts classifyForbidden`). Rate limits (`rateLimitExceeded`, `userRateLimitExceeded`, …) are retried like a 429. A missing scope (`insufficientPermissions`, `ACCESS_TOKEN_SCOPE_INSUFFICIENT`) sends the inbox to `needs_reauth`. Anything else is that message's alone. At ingest, a permanent failure becomes a `failed / fetch_failed` doc in Triage, with no scan charged and no retry button (reprocess answers 409 `nothing_to_reprocess` for any emailed doc with nothing stored). A transient one ends the pass and the part retries next tick, up to `MAX_FETCH_ATTEMPTS` (3) failures of that part before it is given up on the same way; a rate limit is the mailbox's and costs the part no attempt. A transient failure during classification gives back the day's unused classify reservation. At stage 0/1 a permanent failure records the message as `failed`. The sync result's `failed` counts the documents given up on in the run. Logs carry `connId`, `messageId`, status and reason only.
- **Junk-rate telemetry**: `emailIngests` verdicts make per-restaurant precision queryable (ingested vs discarded vs approved). Beta gate: if trailing-30-day discard rate of email-sourced invoices exceeds ~50% for an inbox, raise its classifier threshold and notify — measure before automating more than that.
- **Disconnect/cleanup**: token revoked + deleted, invoices retained, dedup records retained (reconnect-safe), full purge on restaurant deletion.

## Going live after Phase 0

The code is complete and deploys safely as is: nothing email-related is bound to a secret, so production shows "not available in this environment" until these steps run. Do them in this order — a function that declares a secret Secret Manager does not have fails the deploy, so the secrets come before the code that binds them.

1. **The Google OAuth client** (Phase 0 output). In the `teremu-app` Cloud project, Google Auth Platform: a *Web application* client with the scopes `openid`, `email` and `https://www.googleapis.com/auth/gmail.readonly`, and this **authorized redirect URI**, verbatim: `https://app.teremu.com/oauth/email/callback` — `APP_URL` + `EMAIL_OAUTH_CALLBACK_PATH`, which Firebase Hosting rewrites to `emailOauthCallback` (`firebase.json`). Not the function's own `cloudfunctions.net` URL: Google's verification only accepts redirect URIs on domains you own and have verified (`teremu.com`, in Search Console). `EMAIL_OAUTH_REDIRECT_URL` overrides it. **Keep the publishing status *In production* — never switch it to Testing:** it is the whole app's status, and Teremu's Google sign-in runs on the same consent screen, so Testing would limit sign-in itself to the test-user list. Adding `gmail.readonly` to a production app asks for verification of that one new restricted scope; until it is granted, connecting Gmail shows Google's "unverified app" warning and at most 100 users can grant it — enough for a beta — while sign-in keeps its existing approval.
2. **The secrets.** `node scripts/email-secrets.mjs --dry-run` to see what exists, then `node scripts/email-secrets.mjs`: it prompts for `GMAIL_CLIENT_SECRET` (or reads it from the environment) and creates `EMAIL_TOKEN_ENC_KEY` if missing. It never regenerates an existing key — that would orphan every sealed inbox token — and `--rotate` prepends a new one. The script talks to the real project's Secret Manager, so it runs on a machine logged in to it, on purpose, by a person.
3. **The environment** — in `firebase/functions/.env.teremu-app`: `GMAIL_CLIENT_ID=<the client id>` (public, not a secret). Do **not** set `GMAIL_OAUTH_TESTING`: a production app's grants don't expire weekly (that is a Testing-status limit). The flag only exists for a project whose consent screen really is in Testing.
4. **Bind the secrets in code** — done (2026-10-22); listed for the record. Deploying it before step 2 fails:
   - `api.ts`, the `api` function: `secrets: [NVIDIA_API_KEY, STRIPE_SECRET_KEY, ...POS_SECRETS, ...EMAIL_SECRETS]`
   - `index.ts`, `emailSync`: `secrets: [NVIDIA_API_KEY, ...EMAIL_SECRETS]`
   - `emailOauthCallback` needs none (it only redirects).
   - `EMAIL_SECRETS` is exported from `email/index.ts`; delete its "NOT bound yet" comment in the same change.
5. **Deploy** with `node scripts/deploy.mjs` (the test gate runs first). Cloud Scheduler must allow `emailSync`; `firestore.indexes.json` carries the two `emailIngests` indexes the sync and the expiry sweep query.
6. **Check it live** with your own account: Settings → "Facturas por correo" → *Conectar Gmail* → Google's consent (with the "unverified app" warning until the scope is verified) → back in Settings, connected → *Revisar ahora* → the first invoices in Triage with the 📧 badge. `email_ingest_outcome`, `llm_usage` (`email-classify`, `ocr-text`) and the `Email sync` log line are the first things to watch.
7. **When Google verifies the scope:** nothing to change in code — the "unverified app" warning and the 100-user cap simply go away.
8. **The onboarding prompts** (2026-10-29, docs/email-quota-paywall-plan.md Phase 5) — the "¿Te llegan facturas por correo?" block on the setup done screen, the connect button under Triage's empty state, and the tour's email beat — render only when `GET /me` `features.emailImport` is true: a provider is available AND its OAuth app is not flagged as in testing (`emailImportOffered()` in `email/index.ts`, i.e. `GMAIL_OAUTH_TESTING` unset). Flipping `GMAIL_OAUTH_TESTING` off is what turns them on. **Open point:** step 3 leaves that flag unset in production, so as written the prompts appear at go-live, while Google's unverified-app warning still shows until step 7. Keeping them back until verification needs either `GMAIL_OAUTH_TESTING=true` meanwhile (which also shows Settings' weekly-reconnect caveat — wrong for a production-status client) or a flag of its own; decide before step 5. The setup and Triage buttons start the same OAuth flow; every callback URL carries `card=email`, so the browser always lands on the email card in Settings, which finishes the connection and starts the first check.

Abandoned OAuth states (`emailOauthStates`, like `posOauthStates`) are swept by a Firestore TTL policy on their `purgeAt` Timestamp — declared in `firestore.indexes.json`, so step 5's deploy creates it. `expiresAt` stays epoch ms for the code's own check; TTL needs a Timestamp, hence the second field.
